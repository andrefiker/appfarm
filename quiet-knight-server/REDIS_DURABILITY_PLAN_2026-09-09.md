Safe procedure to prepare and rehearse before scheduling the change:

1. Record the exact running Redis image/digest, start command, data directory, RDB filename, `save`, `appendonly`, `appendfsync`, memory/eviction configuration, key count, room versions and remaining TTLs. Record the running server deployment/config as rollback. Resolve the staged patch intentionally.
2. Prove secure, binary-safe transfer out of the live container and into a volume-mounted restore container. Test the same Redis image's restore process on a disposable local copy. A textual log dump is not a backup. Keep any backup encrypted/access-restricted: rooms contain seat credentials.
3. Schedule a short maintenance window. Stop the chess server's active deployment only after confirming it is the sole writer. Keep Redis running while producing the final snapshot. Verify no other writer remains; otherwise do not proceed.
4. Run `BGSAVE`, wait for `rdb_bgsave_in_progress=0` and `rdb_last_bgsave_status=ok`, then transfer the resulting RDB to secure storage. Verify checksum and `redis-check-rdb`. Restore that exact backup locally and compare room counts, versions, FEN and absolute expirations. TTLs must continue expiring, not reset to seven days. Do not proceed without a complete verified backup and a rehearsed restore.
5. Attach a persistent volume at `/data` using Railway's supported service lifecycle. Treat this as a replacement with an initially empty mount. Use a rehearsed bootstrap that restores the verified RDB into the mounted directory with correct ownership before starting Redis, and refuses to start if the expected snapshot is missing or invalid. Never reopen the chess server against an empty store. This bootstrap/transfer mechanism is a prerequisite, not something the current tooling has established.
6. First start from the restored RDB and verify data before enabling AOF. Then enable AOF using the Redis-supported live conversion procedure, wait for the initial AOF rewrite to finish successfully, and persist matching startup configuration. Target `appendonly yes` and `appendfsync everysec`, with periodic RDB backups retained. Do not start with an empty AOF directory that takes precedence over the restored RDB. Confirm all persistence files are on the volume.
7. Reopen the unchanged chess server, run `verify-live.js`, and resume a pre-maintenance room with both seats. Validate FEN/version/TTL and a fresh socket snapshot. Schedule/test Redis restart durability only after the backup and restore are proven.
8. Rollback: keep traffic stopped while restoring the verified snapshot into the same volume using the recorded Redis image/config. Reopen traffic only after state verification. An old deployment image alone cannot recover deleted ephemeral data. Preserve the secure backup until acceptance and recovery retention requirements are met.

The target reduces replacement risk but does not promise zero-loss crash recovery: AOF every-second fsync can lose roughly the last second of writes. Volume backups and restore drills still matter.
